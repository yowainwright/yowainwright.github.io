A few years ago, I had to fix CVE security issues on a project. One way to address those CVEs was with overrides.
Overrides let you tell your package manager which dependency versions to use, but they don't explain why those versions were chosen.

Lots of overrides. I didn't know why they were there, whether they could be removed, or what might happen if I added more.
It felt like a problem that, if unsolved, would lead me to the same situation again.

So, I decided I wanted to build a little logic for our team's overrides.
My idea was to add an object to a `package.json` which explained why each override was there.
This was a win, way better than what we had but still a bit unfulfilling.
I thought we could make providing context to overrides easier and this spawned Pastoralist[1](#source-1).

Recording why an override was there helped, but I also wanted to know whether we still needed it.

<InfoBlock title="Questions Pastoralist Answers">
  <p>Is the package that needed the override still used in the project? Is there a newer version of that package? If we updated it, would we still need the override?</p>
</InfoBlock>

In the original repo where I was fixing CVEs, Pastoralist was a huge optimization.
CVEs went down, we knew why the overrides were there, and we could do that work in seconds instead of hours or more.
Below, I will go over Pastoralist and how it answers the questions above for you.

## The Problem with Overrides

Overrides are a simple, powerful tool. But the more we added, the harder they became to maintain.

A typical `package.json` override block can look like this:

<OverrideExample>

```json
// [title: package.json - undocumented overrides]
{
  "overrides[tooltip:These rules tell the package manager which dependency versions to use. They don’t explain why each rule was added.]": {
    "semver[tooltip:Allows semver 7.5.4 through the remaining 7.x releases. Which dependency needed this override?]": "^7.5.4",
    "ws[tooltip:Allows ws 8.17.1 or later, including later major versions. The minimum version doesn’t tell us what issue it addressed.]": ">=8.17.1",
    "axios[tooltip:Pins axios to exactly 1.12.0. Why this version?]": "1.12.0",
    "lodash[tooltip:Allows lodash 4.17.23 or later. Does anything in the project still need this override?]": ">=4.17.23"
  }
}
```

</OverrideExample>

We can see which versions these overrides allow, but not why they were chosen or whether anything still needs them.

## How Pastoralist Works, A Breakdown

Let's look into how Pastoralist works.

Pastoralist[2](#source-2) helps you with overrides in 3 key ways.

### 1. Track: Understand Each Override

Pastoralist investigates each override to understand the dependency and records that context in its **appendix**:

<AppendixExample>

```json
// [title: package.json - Pastoralist appendix (illustrative data)]
{
  "pastoralist": {
    "appendix[tooltip:The tracking records for your overrides.]": {
      "lodash@>=4.17.23[tooltip:This record belongs to the lodash override at the specified version range.]": {
        "dependents[tooltip:The packages that use this dependency. The names in this example are illustrative.]": {
          "express": "^4.18.0",
          "async": "^3.2.0"
        },
        "ledger[tooltip:Tracking details for this override. Security findings or a maintainer can supply additional context.]": {
          "reason": "Security vulnerability CVE-2021-23337",
          "severity": "high",
          "addedDate[tooltip:When Pastoralist first recorded this override. The override itself may be older.]": "2025-01-15T00:00:00.000Z"
        }
      }
    }
  }
}
```

</AppendixExample>

The appendix records _why_ an override is there, _what_ depends on it, and _when_ Pastoralist first recorded it.

### 2. Scan: Check Security and Usage

Pastoralist checks your dependencies for known security issues. It also checks whether your overrides still match the dependency tree. Security scanning supports six providers: OSV[9](#source-9) (free, no auth required), GitHub Advisory Database, npm audit, Snyk (experimental), Socket (experimental), and Spektion (experimental).

Pastoralist can add overrides for CVEs automatically with `--checkSecurity --forceSecurityRefactor`. It also supports patches you add yourself. Interactive mode lets you choose which fixes to apply.

### 3. Clean: Update the Appendix and Overrides

Pastoralist updates its appendix and overrides based on dependency context, security findings, and usage. Use `--remove-unused` to remove verified unused entries from both, then run your normal CI checks.

## Before and After

This example records the existing override, its dependents, and when Pastoralist first recorded it. It does not add a reason. Reasons can come from security findings or be supplied by the maintainer.

```json
  "name": "shepherd-cli",
  "dependencies": {
    "express": "4.18.2"
  },
  "overrides": {
    "qs": "6.11.2" // [!code hl]
  }
}
```

</section>

<section>

```bash
// [title: Example command]
npx pastoralist
```

</section>

<section>

```json
// [title: package.json - after Pastoralist]
{
  "name": "shepherd-cli",
  "dependencies": {
    "express": "4.18.2"
  },
  "overrides": {
    "qs": "6.11.2"
  },
  "pastoralist": { // [!code hl]
    "appendix[tooltip:The tracking records for your overrides.]": { // [!code hl]
      "qs@6.11.2[tooltip:This record belongs to the qs override at version 6.11.2.]": { // [!code hl]

          "shepherd-cli": "qs (required by express)" // [!code hl]
        }, // [!code hl]
        "ledger[tooltip:Tracking details for this override. Security findings or a maintainer can supply additional context.]": { // [!code hl]
          "addedDate[tooltip:When Pastoralist first recorded this override. The override itself may be older.]": "2026-10-16" // [!code hl]
        } // [!code hl]
      } // [!code hl]
    } // [!code hl]
  } // [!code hl]
}
```

## Conclusion

There are a few key things I don't want you to miss in this article!

1. Overrides are a good tool for pinning dependency versions.
2. Pastoralist checks for security issues and can add dependency overrides to fix them.
3. Pastoralist documents why your overrides exist and cleans up the overrides if they are no longer needed.
4. Pastoralist works in one command: `npx pastoralist --checkSecurity --forceSecurityRefactor --remove-unused`.

Pastoralist has been saving me a lot of time. I am still improving it but it's already giving me joy.
Please give it a star and try it out. Maybe it could save you a lot of time too?!
