A few years ago, I had to fix CVE security issues on a project that already had a bunch of overrides.
I didn't know why any of the overrides were there, whether they could be removed, or what might happen if I added more.
It felt like a problem that could lead to the same complexity I was trying to resolve.

<InfoBlock title="Overrides">
  <p>Overrides are often used to fix CVEs or problems between dependencies. They're useful, but an override alone doesn't explain why it was added.</p>
</InfoBlock>

I decided I wanted to build a little logic for our team's overrides.
My idea was to add an object to a `package.json` which explained why each override was there.
This was a small win, but way better than what we had. After building this, I thought we could make providing context to overrides easier
and this spawned Pastoralist[1](#source-1).

Pastoralist provides some nice context for users regarding overrides but c'mon, another object in a `package.json` file?
I felt like most users don't use or care about overrides every day. So, I wanted Pastoralist to provide more value.

<InfoBlock title="Questions I wanted to answer">
  <p>Was the package that needed the override still used in the project? Was there a newer version of that package? If we updated it, would we still need the override?</p>
</InfoBlock>

In the original repo where I was fixing CVEs, Pastoralist was a huge optimization.
CVEs went down, we knew why the overrides were there, and we could do that work in seconds instead of hours or more.
This was just the start though and, hopefully, below I can get you excited about Pastoralist, or at least the logic, as well.

---

## TL;DR

- If your repo uses `overrides`, `resolutions`, or `pnpm.overrides`, Pastoralist[1](#source-1) will document why packages are in overrides.
- Pastoralist can also find stale overrides and remove them with `--remove-unused`.
- Pastoralist can also use OSV, or other supported security providers, to check your project's dependencies for security issues and resolve as many as possible using best case algorithms when enabled.

A typical `package.json` override block can look like this:

```json
// [title: package.json - undocumented overrides]
{
  "overrides[tooltip:These rules tell the package manager which dependency versions to use. They don’t explain why each rule was added.]": {
    "semver[tooltip:Allows semver 7.5.4 through the remaining 7.x releases. Which dependency needed this override?]": "^7.5.4",
    "ws[tooltip:Allows ws 8.17.1 or later, including later major versions. The minimum version doesn’t tell us what issue it addressed.]": ">=8.17.1",
    "axios[tooltip:Pins axios to exactly 1.12.0. Why this version?]": "1.12.0",
    "lodash[tooltip:Allows lodash 4.17.23 or later. Does anything in the project still need this override?]": ">=4.17.23"
  }
}
```

</ScrollyCode>

When reviewing that block later, a maintainer usually needs to answer:

1. _Why_ is each override here?
2. Which packages in your dependency tree actually depend on it?
3. Is the package still needed?
4. Did a new CVE show up since you pinned it?

## Quick review of overrides in five OSS projects

To prove why Pastoralist is cool and how it can help out with overrides and CVE security issues, let's look at a few popular FOSS projects I enjoy.

### Initial Override Snapshot

| Project | Field | Overrides |
| ------- | ----- | --------: |
| **n8n**[4](#source-4) | `pnpm.overrides` | 58 |
| **TanStack Router**[5](#source-5) | `pnpm.overrides` | 51 |
| **Cal.com**[6](#source-6) | `resolutions` | 41 |
| **Next.js**[7](#source-7) | `pnpm.overrides` | 16 |
| **Prisma**[8](#source-8) | `pnpm.overrides` | 5 |

<figcaption>These five projects had 171 overrides before cleanup.</figcaption>

---

**n8n** had 58 overrides: some for security patches (`ws`, `semver`, `axios`), some compatibility pins (`date-fns`, `chokidar`, `esbuild`), some forks (`expr-eval@2.0.2` remapped to `npm:expr-eval-fork@3.0.0`).

**Prisma** had 5 overrides that all appeared security-related.
The `>=` ranges suggest "at least this version to patch a CVE," but the CVE context is not visible from the entry itself.

### Are all of those overrides still needed?

To demonstrate Pastoralist’s cleanup, I ran it on the same five projects. I wanted to see if it could find overrides that no longer matched their dependency trees.

### Unused Override Cleanup Sample

| Project | Overrides | Unused | Unused % |
| ------- | --------: | -----: | -------: |
| **n8n**[4](#source-4) | 58 | 56 | 97% |
| **TanStack Router**[5](#source-5) | 51 | 41 | 80% |
| **Cal.com**[6](#source-6) | 41 | 35 | 85% |
| **Next.js**[7](#source-7) | 16 | 3 | 19% |
| **Prisma**[8](#source-8) | 5 | 5 | 100% |

<figcaption>In this sample, 140 of 171 tested overrides no longer matched anything in the current dependency tree, or 82%!</figcaption>

<PastoralistStudyCharts />

In Prisma, all 5 overrides were security patches for packages that had since left the dependency tree!
So many of these overrides appear to be outdated!

## How Pastoralist Works, A Breakdown

Pastoralist[2](#source-2) helps you with overrides in 3 key ways.

### 1. Track

When you run `pastoralist`, it scans your overrides and builds an **appendix** that documents each one:

<ScrollyCode steps='[
  {
    "title": "Appendix",
    "note": "The tracking records for your overrides.",
    "lines": [
      3
    ]
  },
  {
    "title": "Override",
    "note": "This record belongs to the lodash override at the specified version range.",
    "lines": [
      4
    ]
  },
  {
    "title": "Dependents",
    "note": "The packages that use this dependency. The names in this example are illustrative.",
    "lines": [
      5,
      6,
      7,
      8
    ]
  },
  {
    "title": "Ledger",
    "anchor": "Security vulnerability CVE-2021-23337",
    "note": "Tracking details for this override. Security findings or a maintainer can supply additional context.",
    "lines": [
      9,
      10,
      11,
      12,
      13
    ]
  },
  {
    "title": "Added",
    "note": "When Pastoralist first recorded this override. The override itself may be older.",
    "lines": [
      12
    ]
  }
]'>

```json
// [title: package.json - Pastoralist appendix (illustrative data)]
{
  "pastoralist": {
    "appendix[tooltip:The tracking records for your overrides.]": {
      "lodash@>=4.17.23[tooltip:This record belongs to the lodash override at the specified version range.]": {
        "dependents[tooltip:The packages that use this dependency. The names in this example are illustrative.]": {
          "express": "^4.18.0",
          "async": "^3.2.0"
        },
        "ledger[tooltip:Tracking details for this override. Security findings or a maintainer can supply additional context.]": {
          "reason": "Security vulnerability CVE-2021-23337",
          "severity": "high",
          "addedDate[tooltip:When Pastoralist first recorded this override. The override itself may be older.]": "2025-01-15T00:00:00.000Z"
        }
      }
    }
  }
}
```

</ScrollyCode>

The appendix records _why_ an override is there, _what_ depends on it, and _when_ it was added.

### 2. Scan

Pastoralist can check your overrides against vulnerability databases using six providers: OSV (free, no auth required), GitHub Advisory Database, npm audit, Snyk (experimental), Socket (experimental), and Spektion (experimental).

Pastoralist can add overrides for CVEs automatically with `--checkSecurity --forceSecurityRefactor`. It also supports patches you add yourself. Interactive mode lets you choose which fixes to apply.

### 3. Clean

Overrides that are no longer needed get flagged for removal. If the parent dependency updated and no longer pulls in the vulnerable version, Pastoralist can tell you the override is stale and can be removed after your normal CI checks pass.

React Router and TanStack Hotkeys need separate validation because their workspace-only override shape triggered removal behavior instead of producing appendix entries.
I'd appreciate help testing these cases.

## Conclusion

There is a key thing I don't want you to miss. Pastoralist checks for security issues, documents your overrides, and cleans up the ones you no longer need. All in one command: `npx pastoralist --checkSecurity --forceSecurityRefactor --remove-unused`.
It's not a black box. It's built with FOSS APIs like OSV[9](#source-9), node:fs[10](#source-10), a few bespoke TUI modules[11](#source-11), and probability algorithms[12](#source-12).
