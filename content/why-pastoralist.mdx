An override in package.json can be easy to add and hard to explain six months later.

A CVE shows up in a transitive dependency, so you pin a safer version and merge the PR.
Six months later, the override is still there. Does the project still need it?
If nobody knows, it often stays.

Compatibility workarounds and other temporary pins leave the same question.
[Pastoralist](https://yowainwright.github.io/pastoralist/)[1](https://yowainwright.github.io/pastoralist/) keeps a record of why those overrides exist and helps you check whether you still need them.

---

## TL;DR

If your repo uses `overrides`, `resolutions`, or `pnpm.overrides`, [Pastoralist](https://yowainwright.github.io/pastoralist/)[1](https://yowainwright.github.io/pastoralist/) can document the reason for each pin and flag entries that no longer match your dependency tree. You can review that record when a security patch or compatibility workaround has outlived the PR that introduced it.

I would appreciate help testing it with different package managers, monorepos, and security workflows. Bug reports, awkward edge cases, feedback, and PRs are all welcome.

---

## The Problem

A typical `package.json` override block can look like this:

```json
// [title: package.json - undocumented overrides]
{
  "overrides": {
    "semver": "^7.5.4",
    "ws": ">=8.17.1",
    "axios": "1.12.0",
    "lodash": ">=4.17.23"
  }
}
```

Looking at that block, can you tell:

1. _Why_ is each override here?
2. Which packages in your dependency tree actually depend on it?
3. Is the package still needed?
4. Did a new CVE show up since you pinned it?

`package.json` usually gives you the versions without the answers. Someone reviewing the overrides later needs the reasons too.

---

n8n had 58 overrides with several apparent purposes. Packages like `ws`, `semver`, and `axios` look like security patches, while `date-fns`, `chokidar`, and `esbuild` look like compatibility pins. There are also forks: `expr-eval@2.0.2` is remapped to `npm:expr-eval-fork@3.0.0`. Recording the history near those entries would make it easier to understand the mix.

All 5 of Prisma's overrides appeared security-related. The `>=` ranges suggest "at least this version to patch a CVE," but the entries don't identify the CVEs.

Supabase had 4 overrides when this was first written and has since removed all of them. That's the process Pastoralist is meant to help with: keep the reason while you need a pin, then remove the pin when you don't.

React had fewer entries, but its pin of `jsdom` to `22.1.0` leaves the same question. Was it for security, compatibility, or the test environment? The reason often lives somewhere outside `package.json`.

### What's actually still needed?

Those counts tell us how many overrides someone may need to investigate. They don't tell us whether the overrides still match the dependency tree.

For that, I ran Pastoralist against five larger override sets:

### Unused Override Cleanup Sample

| Project         | Overrides | Unused | Unused % |
| --------------- | --------: | -----: | -------: |
| n8n             |        58 |     56 |      97% |
| TanStack Router |        51 |     41 |      80% |
| Cal.com         |        41 |     35 |      85% |
| Next.js         |        16 |      3 |      19% |
| Prisma          |         5 |      5 |     100% |

In this sample, 140 of 171 tested overrides no longer matched anything in the dependency tree. That's 82%.

Prisma is a useful example here. All 5 overrides were security patches for packages that had since left the dependency tree. The entries weren't harmful, but someone looking at them would still have old security decisions to sort through.

## What Pastoralist Does

[Pastoralist](https://github.com/yowainwright/pastoralist) handles the record keeping, security checks, and cleanup described above. Here's how each part works.

### 1. Track

When you run `pastoralist`, it scans your overrides and builds an appendix with an entry for each one:

```json
// [title: package.json - Pastoralist appendix]
{
  "pastoralist": {
    "appendix": {
      "lodash@>=4.17.23": {
        "dependents": {
          "express": "^4.18.0",
          "async": "^3.2.0"
        },
        "ledger": {
          "reason": "Security vulnerability CVE-2021-23337",
          "severity": "high",
          "addedDate": "2025-01-15T00:00:00.000Z"
        }
      }
    }
  }
}
```

The appendix keeps the reason, dependents, and date alongside the override. Someone reviewing it later can read those details without having to remember the change or find the old PR.

### 2. Scan

Pastoralist can check your overrides against vulnerability databases through 4 providers:

- OSV (free, no auth required)
- GitHub Advisory Database
- Snyk
- Socket

If a new CVE affects one of your overridden packages, Pastoralist can flag it and help generate a fix. Interactive mode lets you choose which fixes to apply.

### 3. Clean

Pastoralist flags overrides that are no longer needed. For example, a parent dependency may have updated and stopped pulling in the vulnerable version. You can review the stale override and remove it after your normal CI checks pass.

That lets you add a pin quickly during an incident and keep enough context to review it once the dependency tree catches up.

## Before and After

Before running Pastoralist, this entry gives you a version without a reason:

```json
// [title: package.json - before Pastoralist]
{
  "overrides": {
    "trim": "^0.0.3"
  }
}
```

Afterward, the appendix records the dependency and the security issue behind the override:

```json
// [title: package.json - after Pastoralist]
{
  "overrides": {
    "trim": "^0.0.3"
  },
  "pastoralist": {
    "appendix": {
      "trim@^0.0.3": {
        "dependents": {
          "remark-parse": "4.0.0"
        },
        "ledger": {
          "addedDate": "2025-01-15T00:00:00.000Z",
          "reason": "Security vulnerability",
          "severity": "high",
          "cve": "CVE-2020-7753"
        }
      }
    }
  }
}
```

## CI/CD

Pastoralist ships as a GitHub Action with three modes[2](https://github.com/yowainwright/pastoralist):

- `check` validates that overrides are documented and current. It fails on vulnerabilities when `fail-on-security` is enabled.
- `update` updates overrides and the appendix in place.
- `pr` creates a pull request with the changes.

For a weekly maintenance PR, the workflow looks like this:

```yml
# [title: .github/workflows/pastoralist.yml]
name: pastoralist
on:
  schedule:
    - cron: "0 5 * * 1"
jobs:
  update:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: yowainwright/pastoralist@v1
        with:
          mode: pr
          check-security: true
          fail-on-security: true
```

For CI pipelines, `--quiet --checkSecurity` exits with code 1 if vulnerabilities are found. You can also use JSON output in scripts.

## Monorepo Support

Pastoralist detects the `workspaces` field in your `package.json`. Set `depPaths: "workspace"` to scan all workspace packages. The appendix stays at the root.

## Getting Started

```bash
# [title: Install Pastoralist]
npm i pastoralist -D
```

Then run it:

```bash
# [title: Run Pastoralist]
npx pastoralist
```

Or add it to `postinstall`:

```json
// [title: package.json - postinstall]
{
  "scripts": {
    "postinstall": "pastoralist"
  }
}
```

Pastoralist works with npm, yarn, pnpm, and bun. The [docs site](https://yowainwright.github.io/pastoralist/) has interactive demos and StackBlitz sandboxes if you'd like to try it without installing anything.

## How fast is it?

I also timed runs against seven projects, including the five in the cleanup sample. Each run included a full OSV security scan (`--checkSecurity --securityProvider osv`), which needs no API key or authentication:

### Pastoralist Scan Timing Sample

| Project         | Overrides |    Time |
| --------------- | --------: | ------: |
| n8n             |        58 |   416ms |
| TanStack Router |        51 |   252ms |
| Cal.com         |        41 |   406ms |
| Storybook       |        19 |   177ms |
| Next.js         |        16 | 1,050ms |
| Prisma          |         5 |   196ms |
| React Router    |         0 |   108ms |

The median run was 252ms. The three largest override sets all finished under 500ms, network call included. Next.js took 1,050ms because it also evaluates patch files alongside its overrides. React Router had no overrides and finished in 108ms.

Those timings make it reasonable to run in CI or as a weekly scheduled PR without adding much time.

## Why This Exists

Pastoralist grew out of the same maintenance problem behind my posts about [building your own Dependabot](/build-your-own-dependabot) and [Snyk and Dependabot ignore configs](/snyk-dependabot-ignore-configs). Those tools help with dependencies. Keeping track of an override from the day you add it to the day you remove it still tends to fall between dependency management and security scanning.

Pastoralist can already help document and clean up overrides. I'd especially appreciate feedback on package-manager edge cases, workspace layouts, security provider integrations, and how it fits into CI.

If you have overrides to maintain, try it and tell me where it works or falls short. If you don't have any yet, starting with a clean baseline can make the first emergency pin easier to review later.
~Thanks!
